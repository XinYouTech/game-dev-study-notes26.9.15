一、《引擎设置》：
1.【渲染器选择】：无脑选“兼容”
　　
1.【对我来说】：
　　——无脑直接使用“Compatibility”渲染器！
　　·【Compatibility(兼容)】：无论是Godot 官方文档还是社区共识，对于2D游戏或不需要高级3D渲染功能的项目，【Compatibility】都是默认和首选的渲染器。
　　·【Compatibility】专注2D性能，而【Forward+】是为高端3D游戏设计的“重武器”。对于2D游戏，它的大部分功能都用不上，反而可能带来不必要的性能开销。
　　·启动与运行效率：【Compatibility】渲染器基于更轻量级的OpenGL/WebGL，启动更快，在2D场景下的性能表现通常非常稳定。
　　·如果2D游戏必须使用【Forward+】才支持的高级计算着色器(Compute Shaders)来实现某些极其复杂的视觉效果，那么你可以考虑它。但是我个人开发最忌讳复杂视觉效果！
#——|——|——
2.【概述】：
　　Godot4在新建项目时提供了三种渲染器选项：“Forward+”、“Mobile(移动)”和“Compatibility(兼容)”。选择哪个渲染器，主要取决于你的目标平台和游戏类型。
　　·选择渲染器的第一标准是你的目标平台：如为Web发布游戏，【Compatibility】是唯一选择；如为手机开发 3D 游戏，【Mobile】是更稳妥的起点。
　　·其次考虑：游戏类型与画面需求**。2D 游戏或画面风格简单的 3D 游戏，【Compatibility】通常是最高效的选择。
　　·最后记住：并非一锤定音。在Godot编辑器的右上角，你可以随时点击切换渲染器。项目初期如果拿不准，可以先选一个开始，后续再根据测试结果调整。不过要注意，切换后可能需要手动调整场景、光照和材质等设置。
3.【Forward+】：追求极致画质的桌面之选
　　·核心定位：这是 Godot 4 中功能最先进、画质最高的渲染器。
　　·渲染后端：基于 Vulkan、Direct3D 12 或 Metal 等现代底层图形 API。
　　·最佳搭档：**现代桌面 PC** 和 **高端 3D 游戏**。如果你的目标是制作一款画面出色的 3A 级或独立 3D 游戏，并主要面向 PC 平台，Forward+ 是首选。
　　·简单总结：要**画质**，选 Forward+。
4.【Mobile】：性能与画质的平衡大师
　　·核心定位：为移动设备(手机、平板)和部分 XR 设备优化的渲染器。
　　·渲染后端：与 Forward+ 相同，也使用 Vulkan、Direct3D 12 或 Metal。
　　·适用领域：要“性能”，选“Mobile”。
　　为手机开发3D游戏，“Mobile”是更稳妥的起点。Android/iOS 设备、XR设备，或需要“同时兼顾移动和桌面平台”的项目。
5.【Compatibility】：无处不在的万能钥匙
　　·核心定位：兼容性最广的渲染器，目标是让游戏能在最多设备上运行。
　　·渲染后端：基于更通用的 OpenGL 3.3 / OpenGL ES 3.0 / WebGL 2.0。
　　·适用领域：要“兼容”，选“Compatibility”。
　　Web首选。Web 平台(HTML5)、老旧或低配置设备，以及绝大多数2D游戏和对画面要求不高的3D游戏。

　　    *   勾选使用外部编辑器(Use External Editor)。
　　    *   在可执行文件路径(Exec Path)中，填入 VS Code 的启动程序路径：
　　        *   **Windows**:C:\Users\[你的用户名]\AppData\Local\Programs\Microsoft VS Code\Code.exe
　　        *   **macOS**:/Applications/Visual Studio Code.app/Contents/MacOS/Electron
　　        *   **Linux**:/usr/bin/code

　　·安装 VS Code 插件：在 VS Code 扩展商店安装 **Godot Tools** 插件，以获得语法高亮、代码补全和调试支持。

3.【节点里有啥——文本角度】：
　　一个节点（“Node”实例）在运行时（内存里）由“三块核心区域”组成：
···1：【对象头（Object Head）】—— 所有 Godot 对象的出厂设置
　　因为“Node”继承自“Object”，所以每个节点实例的“内存首地址”固定包含：
　　·[虚表指针（VTable Pointer）]：占 8 字节（64位系统）。指向 `Node` 类的函数表。这就是“多态”的根源——当你调用 `queue_free()` 时，CPU 通过这张表找到真正的函数地址。
　　·[元数据（Metadata）]：存着一串键值对（`Dictionary` 类型）。你在代码里用 `set_meta("键", "值")` 存的东西全放在这里。
　　·[脚本引用（Script Reference）]：如果你挂了 `.gd` 脚本，这里存着一个指向脚本实例的指针。
···2：【核心数据区（Core Data）】—— Node 类的私有成员变量
　　这是 `Node` 类本身定义的数据，在 `scene/main/node.h` 源码里写得清清楚楚：
　　·[父节点指针（`parent`）]：指向其在场景树中的父节点。
　　·[子节点列表（`children`）]：一个动态数组（`List` 或 `Vector`），存放所有直接子节点的指针。**注意：存的是指针，不是拷贝。**
　　·[名称（`name`）]：一个 `StringName`（内部是唯一的哈希值，不是普通字符串），你在编辑器里改节点名，改的就是这里。
　　·[所有者指针（`owner`）]：标记此节点属于哪个主场景，用于序列化。
　　·[组列表（`groups`）]：一个哈希集合，存储该节点被加入的所有组名（`StringName`）。
　　·[处理标志位（`processing_flags`）]：一个整数位掩码，记录 `_process`、`_physics_process`、`_input` 是否被开启。
···3：【脚本扩展区（Script Extension）】—— 你写的自定义属性
　　当你的 `.gd` 脚本用 `extends Node` 并定义了 `var 血量 = 100` 后：
　　·[]:引擎会为该节点的实例额外分配一块动态内存，用来存储你在脚本里定义的所有成员变量（`血量`、`攻击力`、`技能列表`等）。
　　·[]:这块区域紧跟在核心数据区后面，通过脚本引用（Script Reference）指针找到内存布局，按顺序存放这些值。
····4：绝对没有的东西：
　　·[没有“内置图片”]：节点不存图片像素，只存一个指向“Texture2D”资源的“指针”。图片数据躺在资源系统（“ResourceCache”）里，多个节点可以共享同一块纹理内存。
　　·[没有“死代码”]：`_process` 函数体本身不占节点内存。函数编译后的机器码位于硬盘/内存的代码段（Code Segment），只存一份，所有同类型节点共享。节点里只存指向该函数入口的地址（通过虚表）。

2.【流程理解】：
　　先项目后场景：项目是硬盘上的整个游戏文件夹，场景是项目下的文件——从大到小。
···【场景 → PackedScene → 实例】：
　　场景是硬盘上的.tscn，PackedScene 是加载进内存的“冷冻模板”，实例是用instantiate()解冻出来的“活体”——沿着“设计→加载→运行”的时间线。
···【节点 → 脚本 → 资源】：
　　节点是最小零件，脚本赋予零件行为，资源提供零件数据——“零件→行为→数据”的三位一体。
···【类 → 对象 → 实例 → 类型】：
　　类定义模板，对象是顶层基类，实例是具体拷贝，类型是身份标签——从蓝图到成品再到标签。
···【实体 → 组件】：
　　实体是完整的“角色”，组件是给角色加装的功能插件——整体与部分。
···【场景树 → 信号 → 组 → 单例】：
　　这四项都是运行时机制——舞台、通信、调度、全局管理。把它们放在最后，形成“有了零件(节点)，有了角色(实体)，然后放进舞台(场景树)，用信号和组管理，由单例统筹”的完整叙事。

1.【项目(Project)】：
···<本质解释>：
　　“项目”是Godot游戏工程的“根目录”。
　　//它包含了游戏“全部的全部”，是一个“无限”的概念，是承载规则与规则编织物的地点。
　　它包含了一个核心的“project.godot”配置文件以及游戏所有的资源文件(场景、脚本、图片、音频等)。
···<具体解释>：
　　你在文件系统里看到的整个游戏文件夹就是一个“项目”。它定义了游戏的所有设置，如渲染方式、输入映射、自动加载的全局单例等。
···“res://”是Godot引擎中一个特殊的“路径前缀”，代表“资源(Resource)”的缩写。它就像项目里的一个“根目录锚点”，其定位规则如下：
　　·指向项目根目录：“res://”的指向永远是包含“project.godot”文件的文件夹。
　　·与项目文件夹绑定：它的路径完全取决于你的项目在电脑硬盘上的实际位置。只要项目文件夹被移动或重命名，“res://”的指向就会跟着改变。
　　简单来说，在代码中你可以用它来访问所有游戏资源。例如，要加载项目根目录下的“icon.png”图片，路径就是“res://icon.png”。
　　·“res://”指向的“项目文件夹”在导出并发布后的游戏里是“只读”的。因此，像“玩家存档、游戏设置、日志文件”等需要随时读写的动态数据，不能保存在“res://”路径下。
　　·对于这类动态数据，Godot提供了另一个特殊路径前缀“user://”，它指向用户设备上一个专门用于存储游戏数据的可读写文件夹。

5.【实体(Entity)】：指代有完整逻辑的节点组合

二、《项目结构》：
1.【文件路径】：
　　在 Godot 中，文件路径系统由“三大前缀”、“一套转换规则”、“一套操作API”构成：
1.【三大路径前缀】：基石
···res://【Resources(资源)】：
　　·指向位置：项目根文件夹(包含“project.godot”的目录)
　　·读写权限：只读(导出后打包进 PCK，不可写)
　　·典型用途：加载图片、场景、音频、脚本等所有游戏自带资源 |
···user://【User Data(用户数据)】：
　　·指向位置：操作系统的用户专用数据目录
　　·读写权限：可读写
　　·典型用途：保存存档、配置文件、日志、截图 |
···uid://【Unique ID(唯一标识符)】：
　　·指向位置：Godot 4.0+ 引入的资源引用方式，不指向文件夹，而是指向**资源的唯一身份证号。
　　·读写权限：只读(引擎解析)。
　　·典型用途：替代硬编码路径引用，防止移动文件后路径失效(在“.tscn”/“.tres”中自动生成)。
　　·当你把文件拖进场景时，Godot 4 默认会写成 `uid://xxxxxxx` 而非 `res://xxx.png`。它的好处是即使你重命名或移动了图片文件，只要引擎能通过 UID 找到它，引用就不会断。
#——|——|——
2.【路径转换】：让 Godot 和操作系统互相翻译
···ProjectSettings.globalize_path("res://xxx")：将 Godot 路径转成“操作系统绝对路径”
　　·输入："res://assets/1.png"
　　·输出："C:/MyGame/assets/1.png"
···ProjectSettings.localize_path("C:/MyGame/xxx")：将操作系统绝对路径转成“Godot 路径”
　　·输入："C:/MyGame/assets/1.png"
　　·输出："res://assets/1.png"

·注意：“user://”的绝对路径在不同操作系统上不同，转换规则同样适用。

3.【路径操作 API】：对字符串路径进行拆解
　　在 GDScript 中，“String”类型自带了一套路径处理方法：
···get_base_dir()：获取路径的父目录
···get_file()：获取文件名(含扩展名)
···get_basename()：获取文件名(不含扩展名)
···get_extension()：获取扩展名
···path_join(file)：安全拼接路径(自动处理 `/`)
···replace_extension(ext)：替换扩展名
4.【文件与文件夹的操作类】：读写磁盘
当你要实际读写文件时，使用以下两个核心类：
···FileAccess：读写文件内容(文本/二进制) | `file_open()`、`get_as_text()`、`store_string()`、`store_var()`、`get_var()` |
···DirAccess：管理目录和文件(增删查) | `dir_open()`、`list_dir_begin()`、`get_next()`、`make_dir()`、`remove()`、`rename()` |

**存储/读取变量的快捷方式**(省去手动序列化)：
·ResourceSaver.save()`：将一个 `Resource` 对象直接保存为 `.tres` 或 `.res` 文件。
·ResourceLoader.load()`：从 `res://` 路径加载一个资源。
5.【路径分隔符铁律】：跨平台注意事项
·Godot **内部统一使用 `/`**(正斜杠)。在 Godot 路径字符串中，**永远不要写 `\`(反斜杠)**。
·当你用 `globalize_path()` 拿到操作系统绝对路径后，Windows 会返回 `\`，但此时该路径已经交给操作系统 API 处理了，无需你再处理。
6.【“res://”在导出后的物理真相】：
···开发时(编辑器)：直接对应项目文件夹，你可以随意新建、删除文件。
···导出后(单包 PCK)：被压缩打包进“game.pck”文件，不再对应硬盘上的文件夹。此时“FileAccess.open("res://xxx")”只能读无法写，且“DirAccess”对“res://”的操作会受限。
因此：任何需要写入的操作，必须全部使用“user://”。
